# 01
## Резюме для руководства

---

# Предмет проекта

**Локальная AI-платформа** на собственной инфраструктуре:

- Inference крупных языковых моделей (70B и 35B MoE)
- Корпоративная база знаний (RAG) по документам фирмы
- Специализированные агенты для инженерных процессов

Исходные данные проектов (ТЗ, схемы, BOM, исходный код) обрабатываются **внутри периметра** организации.

---

# Бизнес-проблемы и ответ системы

| Проблема | Решение |
|----------|---------|
| Использование публичных LLM с конфиденциальными данными | Контролируемый локальный контур |
| Длительный поиск в даташитах и внутренних спецификациях | RAG по корпоративной базе |
| Высокая трудоёмкость review документов и BOM | Агенты для первичного прохода |
| Рост переменных затрат на API | Фиксированный CapEx, нулевая стоимость токена |
| Потеря проектного опыта между итерациями | Накопление lessons learned |

---

# 02
## Архитектура

---

# Логическая схема

```
Пользовательский слой     VS Code / Open WebUI / внутренний портал
                                    │
                         API Gateway, аутентификация, маршрутизация
                          ╱                              ╲
               Агентный контур (LangGraph, MCP)    Прямой чат
                          ╲                              ╱
                         RAG (Qdrant) + Inference (vLLM)
                              GPU0: 70B    GPU1: 35B
                                    │
              Хранилища: Postgres, журналы аудита, мониторинг
```

---

# Архитектурные принципы

1. **Разделение ролей:** inference (vLLM) отделён от логики агентов (LangGraph).
2. **Две GPU** используются как **два независимых inference-контура**, не постоянный tensor parallel.
3. **RAG обязателен** для задач, связанных с компонентами, номиналами и внутренними правилами.
4. **Доступ в интернет** — только через выделенный proxy с DLP (при включении).
5. **Финальное решение по критичным задачам** остаётся за инженером (human-in-the-loop).

## Аппаратная платформа

---

# Целевая конфигурация сервера

| Компонент | Спецификация |
|-----------|--------------|
| GPU | 2× NVIDIA RTX 4090D, 48 GB VRAM |
| CPU | Workstation-класс: Threadripper / EPYC / Ryzen |
| Оперативная память | 256 GB (минимум 128 GB) |
| Накопитель | 4 TB NVMe (модели) + 1 TB (ОС) |
| Блок питания | 1600 W |
| Суммарный VRAM | 96 GB |

---

# Особенности RTX 4090D 48 GB

Официальная поставка NVIDIA — **24 GB**. Конфигурация **48 GB** — модифицированная (clamshell PCB, изменённый VBIOS).

| Параметр | Значение |
|----------|----------|
| Производительность LLM | ~96–97% от RTX 4090 |
| Охлаждение | Преимущественно blower; повышенный уровень шума |
| Гарантийная поддержка | Ограничена; требуется приёмочное тестирование |
| Критичное требование к плате | PCIe x8/x8 минимум на слотах GPU |

---

# Сравнение: 48 GB vs 24 GB (суммарно на 2 GPU)

| Возможность | 2×24 GB | 2×48 GB |
|-------------|:-------:|:-------:|
| 70B на одной карте | Нет | Да |
| 70B и 35B параллельно | Нет | Да |
| 70B Q8 / контекст 32K | Нет | Да |
| Модели класса 120B (Q4, TP=2) | Нет | Да |

---

# Аппаратный уровень: баланс факторов

| Преимущества | Ограничения | Ключевые риски |
|--------------|-------------|----------------|
| Высокая плотность VRAM на 2 GPU | Кастомные карты — нестабильность | PCIe x4 на слотах |
| Параллельные модели без TP | Высокое энергопотребление | Перегрев при плохом airflow |
| Низкая переменная стоимость inference | Отсутствие NVLink | Некорректный VBIOS |
| 70B без tensor parallel | Нет enterprise SLA NVIDIA | Завышенные ожидания по «96 GB в одной модели» |

## Программный стек

---

# Слой inference

| Компонент | Назначение | Статус |
|-----------|------------|--------|
| Ollama | Пилот, 2–4 недели | Старт |
| vLLM | Production API, concurrent load | Обязательно |
| SGLang | Agent workloads, prefix cache | Опционально |
| NVIDIA NIM | Enterprise-стек NVIDIA | Опционально |

<p class="note">Ollama не рекомендуется как единственный production-слой при нагрузке от команды 5+ человек.</p>

---

# Модели

| Функция | Модель | GPU |
|---------|--------|-----|
| Reasoning, review документов | Llama 3.3 70B AWQ | GPU0 |
| Агенты, код, RAG-ответы | Qwen3.6-35B-A3B | GPU1 |
| Краткие запросы | Qwen3.5-9B | GPU1 |
| Узкая специализация: код | Qwen3-Coder-Next | GPU1 |

Качество reasoning относительно облачных frontier-моделей: порядка 85–90%. По задачам с корпоративной базой — выше за счёт RAG.

---

# RAG — корпоративная база знаний

**Retrieval-Augmented Generation:** перед генерацией ответа система извлекает релевантные фрагменты из внутренних документов.

```
Источники → сегментация → embedding → Qdrant → поиск → LLM → ответ + источник
```

Для hardware-профиля RAG является **обязательным** элементом. Без него возрастает риск ошибок в MPN, номиналах и параметрах компонентов.

---

# RAG: приоритеты наполнения

| Коллекция | Приоритет |
|-----------|-----------|
| Даташиты, design rules | P0 |
| Проекты, lessons learned | P0 |
| История BOM, требования | P1 |
| HDL patterns, style guides | P2 |

Ценность базы **нарастает** при дисциплине пополнения после проектов. Без кураторства — деградация качества поиска.

---

# Агентный контур

| Агент | Модель | Функция |
|-------|--------|---------|
| Design Review | 70B | Первичный review ТЗ и архитектуры |
| BOM Intelligence | 35B | Подбор и проверка компонентов |
| HDL / Code | 35B | Генерация и правка кода, testbench |
| Documentation | 70B / 35B | Черновики документации и traceability |

Стек: LangGraph, Postgres (checkpoints), MCP (интеграции).

# Безопасность и сетевой периметр

| Контур | Меры |
|--------|------|
| Сеть | VLAN; inference-хост без прямого egress |
| Доступ | SSO / LDAP; RBAC по проектам |
| Данные RAG | ACL по идентификатору проекта |
| Агенты | Sandbox FS; Git read-only по умолчанию |
| Интернет | Только через proxy: whitelist, DLP, аудит |

Инструкции в промпте не заменяют технические средства контроля.

# Персонал и трудозатраты

| Этап | FTE | Комментарий |
|------|-----|-------------|
| Пилот | 0,3–0,5 | Совмещение с DevOps / lead |
| Production | 0,5–1,0 | AI Platform Engineer |

Требуемый профиль: Linux, Docker, Python, эксплуатация RAG/LLM. Специализация ML-исследователя не требуется.

Дополнительно: 0,1 FTE senior-инженера на кураторство design rules и eval.

---

# Пропускная способность (96 GB VRAM)

Режим: GPU0 — 70B, GPU1 — 35B.

| Режим нагрузки | Комфортный режим | Предельный |
|----------------|------------------|------------|
| Тяжёлые сессии (70B) | 2 | 3 |
| Лёгкие сессии (35B) | 4–5 | 6–8 |
| Суммарно | 4–6 | 8–10 |

| Размер команды | Достаточность конфигурации |
|----------------|----------------------------|
| 5–15 инженеров | Да |
| 25+ | Требуется очередь или второй сервер |

Ограничивающий фактор — пропускная способность GPU (tok/s), не объём VRAM.

## Внедрение и риски

---

# Дорожная карта (20 недель)

| Фаза | Срок | Содержание |
|------|------|------------|
| 0. Решение | 2 нед. | Go/no-go, закупка, назначение владельца |
| 1. Foundation | 1–4 | vLLM, Open WebUI, RAG P0 |
| 2. RAG production | 5–8 | Pipeline, ACL, IDE-интеграция |
| 3. Agents | 9–14 | LangGraph, MCP, BOM и Docs |
| 4. Hardening | 15–20 | Review/HDL, security, eval ≥75% |
| 5. Эксплуатация | Постоянно | Lessons learned, ревизия базы |

---

# Основные риски

| Риск | Митигация |
|------|-----------|
| Отказ модифицированных GPU | Burn-in; резервный cloud fallback |
| Отсутствие владельца платформы | 0,5 FTE; KPI внедрения |
| Ошибки в подборе компонентов | RAG + citation + утверждение инженером |
| Утечка через интернет | Proxy, DLP, режим Strict |
| Обход в публичные LLM | Политика; удобный локальный интерфейс |
| Ошибка конфигурации PCIe | Workstation-плата x8/x8 |

---

<div class="cols">
<div>

### Критерии GO
- Команда от 5 инженеров
- IP-критичные проекты
- 0,3+ FTE на сопровождение
- Бюджет 10–20 тыс. USD
- Готовность к 4–6 неделям пилота

</div>
<div>

### Критерии NO-GO
- Команда 1–2 человека
- Нет ресурса на RAG и внедрение
- Ожидание полной автономии проектирования
- Отсутствие Linux-эксплуатации

</div>
</div>

---

# Сравнение стратегий

| Подход | Сильные стороны | Слабые стороны |
|--------|-----------------|----------------|
| Без изменений | Нулевые затраты | Утечки IP в облако |
| Только облако | Быстрый старт, топ-модели | Счёт, зависимость, данные |
| Локальная платформа | Контроль, TCO, RAG | CapEx, операционная нагрузка |
| Гибрид (год 2+) | Гибкость | Сложность архитектуры |

Рекомендуемая траектория: локальный контур → точечный cloud overflow для нерегулярных frontier-задач.
