## 1. Резюме для руководства

### Что строим

Локальную AI-платформу на собственном железе: большие языковые модели (LLM), корпоративная база знаний (RAG), AI-агенты для инженерных задач. Данные (ТЗ, схемы, BOM, исходники) **не покидают периметр фирмы** по умолчанию.

### Зачем

| Проблема сегодня | Решение платформы |
|------------------|-------------------|
| Инженеры используют ChatGPT/Claude с конфиденциальными данными | Локальный аналог с полным контролем |
| Повторяющийся поиск в даташитах и спеках | RAG по внутренней базе |
| Долгий review документов и BOM | Агенты на черновой проход |
| Растущие счета за API при активной команде | Предсказуемый CapEx, ~$0 за токен после покупки |
| Потеря опыта между проектами | Накопительная база lessons learned |

### Оценка целесообразности (для инженерной фирмы 5–15 человек)

| Критерий | Оценка |
|----------|--------|
| Общая полезность | **7.5–8 / 10** |
| Окупаемость железа | **3–9 месяцев** при активном use |
| Окупаемость с внедрением | **6–14 месяцев** |
| Реалистичный прирост эффективности | **25–35%** FTE (не замена людей) |
| Сложность внедрения | **Средняя–высокая** |

### Главный вывод

Платформа **оправдана**, если есть конфиденциальные проекты, команда ≥5 инженеров и готовность выделить **0.3–0.5 FTE** на сопровождение. **Не оправдана** как «купили железо и забыли» или как замена senior-инженеров.

## 2. Цели и критерии успеха

### Бизнес-цели

1. **Суверенитет данных** — IP, ТЗ, схемы, BOM не в публичных API.
2. **Ускорение рутины** — документы, review, поиск компонентов, boilerplate-код.
3. **Корпоративная память** — опыт проектов доступен через RAG.
4. **Предсказуемые затраты** — без runaway API bills.

### Технические цели

1. Две крупные модели параллельно (70B + 35B MoE) на 96 GB VRAM.
2. 4–6 одновременных активных сессий в комфортном режиме.
3. RAG с citation (ответ со ссылкой на источник).
4. Аудит запросов и исходящего трафика (если включён интернет).

### KPI успеха (через 6 месяцев)

| KPI | Целевое значение |
|-----|------------------|
| Доля инженеров, использующих систему еженедельно | ≥ 70% |
| Eval pass rate (20 тестовых задач фирмы) | ≥ 75% |
| Среднее время ответа (35B, простой запрос) | < 30 сек |
| Инциденты утечки данных | 0 |
| Экономия времени (опрос + замеры) | ≥ 15 ч/нед на команду |
| Uptime inference (рабочие часы) | ≥ 95% |

```
│                         ПОЛЬЗОВАТЕЛИ                                     │

        │                               │
        ▼                               ▼
┌───────────────────┐         ┌───────────────────┐
│  AGENT RUNTIME    │         │  DIRECT CHAT      │
│  LangGraph        │         │  (без агента)     │
│  + MCP Client     │         │                   │
└─────────┬─────────┘         └─────────┬─────────┘
          │                             │
          └──────────────┬──────────────┘

┌─────────┐       ┌─────────────┐     ┌─────────────┐
│  RAG    │       │  INFERENCE  │     │  MCP        │
│ Qdrant  │       │  vLLM       │     │  Servers    │
│ Embed   │       │  GPU0: 70B  │     │ Git, FS, DB │
└─────────┘       │  GPU1: 35B  │     └──────┬──────┘
                  └─────────────┘            │
                                             ▼
                                    ┌─────────────────┐
                                    │ Search Proxy    │ (опционально)
                                    │ whitelist + DLP │
                                    └────────┬────────┘
                                             ▼
                                         Интернет
┌──────────────────────────────────────────────────────────────────────────┐
│  DATA LAYER: Postgres (agent state, audit) │ Redis (queue) │ NVMe models │
└──────────────────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────────────┐
│  OBSERVABILITY: Langfuse │ Prometheus/Grafana │ Structured logs           │
└──────────────────────────────────────────────────────────────────────────┘
```

### Принципы архитектуры

1. **Разделение inference и агентов** — vLLM только генерирует текст; логика агентов в LangGraph.
2. **Две GPU — два независимых inference-процесса** (предпочтительно), не TP=2 на постоянной основе.
3. **RAG обязателен** для hardware-задач; LLM без RAG — только общие вопросы.
4. **Интернет только через proxy** — LLM-сервер не имеет прямого egress.
5. **Human-in-the-loop** для BOM, safety-critical HDL, финального sign-off.

## 4. Аппаратный уровень

### Целевая конфигурация

| Компонент | Спецификация | Назначение |
|-----------|--------------|------------|
| GPU | 2× RTX 4090D, **48 GB** VRAM each | Inference LLM |
| CPU | AMD Threadripper Pro / EPYC **или** Ryzen 9 + workstation MB | PCIe lanes, параллельная индексация RAG |
| RAM | **256 GB** DDR5 (минимум 128 GB) | RAG indexing, staging, ОС |
| Storage | 4 TB NVMe (модели) + 1 TB (ОС) | Модели 20–80 GB каждая |
| PSU | **1600W** 80+ Platinum | Пик ~900–1000W на GPU |
| Network | 1 GbE (10 GbE опционально) | Доступ команды |
| Chassis | Full tower / 4U rack, активный продув | Blower-GPU гонят тепло в корпус |

### Важно про RTX 4090D 48 GB

Официальная 4090D от NVIDIA — **24 GB**. Версия **48 GB** — кастомная модификация (clamshell PCB, 24 модуля памяти, модифицированный VBIOS). Встречается на рынке Китая / cloud bare-metal.

| Аспект | Детали |
|--------|--------|
| VRAM | 48 GB на карту, та же шина 384-bit |
| Compute | ~96–97% от стандартной 4090 на LLM |
| Охлаждение | Часто blower, **~65 dB** — нужна отдельная комната / rack |
| Гарантия | Неофициальная; риск отказа выше |
| Проверка при покупке | `nvidia-smi` → 49152 MiB; burn-in 48 ч |

### Что даёт 96 GB (vs 48 GB на 2×24 GB)

| Возможность | 2×24 GB | **2×48 GB (96 GB)** |
|-------------|---------|---------------------|
| 70B на одной карте | ❌ | ✅ с большим KV-cache |
| 70B + 35B параллельно | ❌ | ✅ |
| 70B Q8 / длинный контекст 32K | ❌ | ✅ (TP=2 или одна карта Q4) |
| 120B class Q4 | ❌ | ✅ на TP=2 |
| Fine-tune LoRA 32B + inference | ❌ | ✅ |

### Плюсы / минусы / подводные камни

| | |
|--|--|
| **Плюсы** | Топ consumer/workstation сегмент; 70B без tensor parallel; две модели сразу; низкая стоимость токена после покупки |
| **Минусы** | Кастомные 48 GB — риск железа; нет NVLink; шум и энергопотребление; нет enterprise SLA от NVIDIA |
| **Подводные камни** | ① Слоты PCIe x4 — катастрофа для multi-GPU → нужен x8/x8 минимум. ② Blower в закрытом корпусе → thermal throttle. ③ «Память пулится» — **нет**: 96 GB ≠ одна модель на 96 GB без TP; usable ~90 GB с overhead. ④ Покупка без burn-in — риск DOA/нестабильного VBIOS |

### Необходимость

| Вердикт | |
|---------|--|
| **Обязательно** для заявленных целей (70B + агенты + параллельные модели) | ✅ |
| Альтернатива дешевле | 2× RTX 4090 24 GB — хуже, 70B только через TP=2 |
| Альтернатива надёжнее | 2× RTX 6000 Ada 48 GB — дороже, но официальные 48 GB + ECC |

| | |

## 7. Слой моделей (LLM)

### Рекомендуемый набор для 96 GB

| Роль | Модель | GPU | VRAM | Лицензия |
|------|--------|-----|------|----------|
| Reasoning, review, docs | Llama 3.3 70B Instruct AWQ | GPU0 | ~40 GB | Llama Community |
| Агенты, код, RAG-QA | Qwen3.6-35B-A3B AWQ | GPU1 | ~21 GB | Apache 2.0 |
| Быстрые запросы (опц.) | Qwen3.5-9B | GPU1 | ~6 GB | Apache 2.0 |
| Coding specialist (опц.) | Qwen3-Coder-Next | GPU1 | ~45 GB | Apache 2.0 |

### Сравнение типов моделей

| Тип | Плюсы | Минусы | Подводные камни |
|-----|-------|--------|-----------------|
| **Dense 70B** | Стабильный reasoning, предсказуемая latency | Много VRAM | Q2/Q3 — заметная потеря качества |
| **MoE 35B (3B active)** | Быстро, мало VRAM, сильный coding | Все эксперты в VRAM | «35B» в маркетинге ≠ 35B active |
| **Distilled R1 70B** | Пошаговое рассуждение | Длинные ответы, медленнее | Chain-of-thought раздувает счёт |
| **Frontier 120B+ Q4** | Максимум качества локально | Нужен TP=2, медленно | На 96 GB — впритык, мало места под KV |

### Качество vs облако

| Задача | Локально (70B/35B) | Облако (GPT-5/Claude Opus) |
|--------|-------------------|----------------------------|
| Review ТЗ | ~85–90% | 100% |
| RAG по даташитам | **Лучше** (своя база) | Нет доступа к базе |
| Сложный multi-step reasoning | ~80–85% | 100% |
| Конфиденциальность | **100%** | Риск |

### Необходимость

| | |
|--|--|
| Минимум | 1× хорошая модель (35B MoE) — старт |
| Рекомендуется | 70B + 35B — разделение тяжёлых и лёгких задач |
| Избыточно на старте | 4+ модели, постоянный TP=2 на 120B |

### Подводные камни

1. **Гонка за новыми моделями** — обновление каждые 2–3 месяца; нужен eval перед swap.
2. **Лицензия Llama** — attribution, ограничения для 700M MAU (нерелевантно для фирмы).
3. **Квантизация** — AWQ INT4 оптимальна для 70B; Q8 лучше, но нужно больше VRAM.
4. **Контекст** — заявленные 1M токенов ≠ реально на 48 GB (KV-cache съедает VRAM).

## 8. RAG — база знаний

### Что такое RAG (в контексте платформы)

**Retrieval-Augmented Generation** — перед ответом система **ищет** релевантные фрагменты во внутренних документах и передаёт их модели. Модель отвечает **на основе найденного**, а не из «памяти обучения».

### Архитектура RAG

```
Документы (PDF, MD, CSV, DOCX)
        ↓
   Ingestion pipeline (chunking, metadata)
        ↓
   Embedding model (bge-m3 / nomic-embed-text)
        ↓
   Vector DB (Qdrant)
        ↓
   Query → Retriever (vector + optional BM25)
        ↓
   Reranker (опционально)
        ↓
   Top-K chunks + вопрос → LLM → ответ + citations
```

### Структура коллекций

| Коллекция | Содержимое | Приоритет |
|-----------|------------|-----------|
| `datasheets` | PDF даташиты по MPN | P0 |
| `design_rules` | SI/PI, clearance, stackup, power | P0 |
| `projects` | architecture.md, lessons_learned | P0 |
| `requirements` | ТЗ, стандарты | P1 |
| `bom_history` | Approved BOM + обоснования | P1 |
| `hdl_patterns` | Проверенные модули, style guide | P2 |
| `reviews` | Выводы review (не сырые черновики) | P2 |

### Компоненты RAG — плюсы / минусы

| Компонент | Выбор | Плюсы | Минусы | Подводные камни |
|-----------|-------|-------|--------|-----------------|
| **Vector DB** | Qdrant | Простой Docker, фильтры по metadata | Слабее на 100M+ векторов | Без metadata — шум в выдаче |
| **Альтернатива** | pgvector | Если уже есть Postgres | Медленнее на больших объёмах | Индекс rebuild долгий |
| **Embedding** | bge-m3 | Multilingual, хорошее качество | Нагрузка на GPU/CPU | Устаревший индекс при смене embedder |
| **Chunking** | 512–1024 tok + overlap | Баланс точности | Неправильный chunk рвёт таблицы | PDF с таблицами — нужен спец. парсер |
| **Hybrid search** | Vector + BM25 | +15–30% точности | Сложнее | Overkill на старте |
| **Reranker** | bge-reranker | Точнее top-K | +latency | Опционально год 2 |

### Накопительный эффект (польза со временем)

| Срок | Эффект |
|------|--------|
| Месяц 1 | Базовые даташиты — ~30% вопросов |
| Год 1 | + projects, BOM — ~60–70% |
| Год 2–3 | + lessons learned — **корпоративное преимущество** |

**Плато** наступает без кураторства: дубликаты, устаревшие rules, мусор.

### Необходимость

| Вердикт | |
|---------|--|
| Для hardware-фирмы | **ОБЯЗАТЕЛЬНО** — без RAG агенты опасны (галлюцинации MPN, номиналов) |
| Без RAG допустимо | Только общие вопросы, обучение, черновики без фактов |

### Подводные камни

1. «Закинули 10 000 PDF» без структуры → хуже, чем 200 curated docs.
2. Устаревший design rule 2022 года → агент даёт неверный совет.
3. Нет citation в промпте → инженер не проверяет источник.
4. Конфиденциальные и публичные docs в одной коллекции без ACL.

## 9. Агенты и оркестрация

### Что такое агент (в этой платформе)

**Агент** = LLM + цикл «думай → вызывай инструменты → проверяй результат» + память сессии. Не одноразовый чат, а **многошаговая задача**.

### Рекомендуемый фреймворк

**LangGraph** — production-ориентированный, stateful graphs, checkpointing в Postgres.

| Альтернатива | Когда | Плюсы | Минусы |
|--------------|-------|-------|--------|
| **LangGraph** | Production, audit | Контроль, replay, HITL | Кривая обучения |
| **CrewAI** | Быстрый прототип | Простой старт | Меньше контроля |
| **n8n** | Workflow automation | No-code интеграции | Не замена LangGraph для сложной логики |
| **Microsoft Agent Framework** | Azure/.NET стек | Enterprise OTel | Vendor lock-in |

### Четыре целевых агента

| # | Агент | Модель | Инструменты | Польза | Риск |
|---|-------|--------|-------------|--------|------|
| 1 | Design Review | 70B | RAG, Git, FS | Review ТЗ, архитектуры | Пропуск критичного без human sign-off |
| 2 | BOM Intelligence | 35B | RAG, BOM DB | Подбор компонентов | Неверный MPN без RAG |
| 3 | HDL/Code Agent | 35B/Coder | Git, FS, terminal | Testbenches, drivers | Safety-critical без review |
| 4 | Documentation | 70B/35B | RAG, templates | Manuals, test plans | Устаревший шаблон |

### Плюсы / минусы агентов в целом

| Плюсы | Минусы |
|-------|--------|
| Автоматизация 5–20 шаговых задач | Медленнее простого чата (минуты) |
| Доступ к Git, FS, DB через MCP | Ошибка на шаге 7 → каскад |
| Аудит каждого шага (Langfuse) | Требует eval и лимитов итераций |
| Локально — безопасно для IP | Переоценка автономности руководством |

### Подводные камни

1. **Агент с `run_terminal` + интернет** — максимальный риск; разделять.
2. **Бесконечный цикл** — обязателен `max_iterations` (например, 10).
3. **Без eval** — агент «работает», но делает ерунду уверенно.
4. **Один агент на всё** — хуже, чем 4 специализированных с router.

### Необходимость

| Этап | Вердикт |
|------|---------|
| Месяц 1–2 | Только чат + RAG (без агентов) |
| Месяц 3+ | Агент 2 (BOM) и 4 (Docs) — быстрый ROI |
| Месяц 5+ | Агенты 1, 3 — сложнее |
| Избыточно на старте | Multi-agent orchestrator с 5+ субагентами |

## 10. MCP — интеграция с системами фирмы

### Что такое MCP

**Model Context Protocol** — открытый стандарт (Linux Foundation / AAIF) для подключения AI к инструментам: Git, файлы, БД, Slack, и т.д. «USB-C для AI-интеграций».

### Архитектура

```
LangGraph Agent (MCP Client)
        ↓ JSON-RPC 2.0
   MCP Gateway (RBAC, audit, rate limit)
        ↓
   ┌────┬────┬────┬────┐
   Git  FS   DB  Custom
```

### Планируемые MCP-серверы

| Сервер | Назначение | Приоритет |
|--------|------------|-----------|
| `filesystem` | Чтение проектов, спек (sandbox paths) | P0 |
| `git` | Diff, log, blame | P0 |
| `postgres` | BOM DB, audit | P1 |
| `safe_web_search` | Через proxy (см. §14) | P2 |
| `altium_export` / custom | Парсинг BOM из экспорта CAD | P3 |

### Плюсы / минусы

| Плюсы | Минусы |
|-------|--------|
| Стандарт, растущая экосистема | Молодой стандарт, изменения spec |
| Переиспользуемые коннекторы | Custom CAD — писать самим |
| Централизованный audit через gateway | Ошибка в MCP = утечка или порча данных |

### Подводные камни

1. **Filesystem без sandbox** — агент читает `/etc/passwd`, `.env`.
2. **Git write без review** — агент коммитит в main.
3. **MCP ≠ безопасность** — gateway обязателен.
4. **stdio vs HTTP** — production только HTTP с auth.

### Необходимость

**Рекомендуется** с месяца 3+. Без MCP агенты — «чат без рук».

## 12. API Gateway, маршрутизация и очереди

### Зачем

Без gateway GPU0 монополизируют 2 человека на 70B; остальные в простое или OOM.

### Функции Router

```python
# Логика маршрутизации (упрощённо)
if task == "review" or context_tokens > 12000:
    → GPU0 :8000 (70B)
elif task in ("bom", "hdl", "agent"):
    → GPU1 :8001 (35B)
else:
    → GPU1 :8001 (9B fast)  # опционально
```

### Компоненты

| Компонент | Технология | Плюсы | Минусы |
|-----------|------------|-------|--------|
| Gateway | FastAPI + JWT/LDAP | Гибкость | Писать самим |
| Queue | Redis | Fair scheduling | +infra |
| Rate limit | per-user quotas | Защита 70B | Жалобы «медленно» |

### Необходимость

| Команда | Вердикт |
|---------|---------|
| 1–3 человека | Опционально |
| 5–15 | **Рекомендуется** |
| 15+ | **Обязательно** |

## 13. Безопасность и контроль утечек

### Уровни защиты

| Уровень | Меры |
|---------|------|
| Сеть | VLAN для AI-сервера; нет прямого интернета на inference host |
| Доступ | SSO/LDAP; RBAC по проектам |
| Данные | RAG ACL по `project_id`; секретные проекты — отдельная коллекция |
| Агенты | Sandbox FS; Git read-only по умолчанию |
| Аудит | Лог: user, model, tools, tokens (без PII в логах) |
| DLP | На search-proxy (см. §14) |

### Режимы работы

| Режим | Интернет | RAG | Когда |
|-------|----------|-----|-------|
| **Strict** | ❌ | Internal only | Секретные проекты |
| **Research** | Search proxy only | Internal + web fetch | Подбор компонентов |
| **Standard** | Search proxy | Internal | Повседневная работа |

### Подводные камни

1. Промпт «не отправляй данные наружу» **не защита** — только DLP + сеть.
2. Continue.dev с cloud fallback — отключить в настройках.
3. Логи Langfuse с полным текстом ТЗ — сами становятся утечкой.
4. Бэкапы Qdrant/Postgres без шифрования.

## 14. Контролируемый доступ в интернет

### Зачем

Даташиты новых чипов, EOL статусы, errata — нет в RAG до индексации.

### Архитектура

```
Agent → MCP safe_web_search → Search Proxy (DMZ)
                                  ├ whitelist domains
                                  ├ DLP scan query
                                  ├ block POST/upload
                                  └ audit log
                                       ↓
                                   Internet
```

### Whitelist (пример для hardware)

`ti.com`, `analog.com`, `st.com`, `nvidia.com`, `digikey.com`, `mouser.com`, `octopart.com`, `ipc.org`

### Что разрешено / запрещено в query

| Разрешено | Запрещено |
|-----------|-----------|
| MPN, публичные параметры | Текст ТЗ, имена клиентов |
| `site:ti.com TPS62840` | Полный BOM проекта |
| Публичные стандарты | Пути `\\server\projects\` |

### Плюсы / минусы

| Плюсы | Минусы |
|-------|--------|
| +20–30% полезности vs чистый RAG | Риск утечки при ошибке DLP |
| Актуальные даташиты | Нужен отдельный proxy VM |
| Меньше ручного поиска | Ложные срабатывания DLP |

### Необходимость

**Опционально**, месяц 4+ после стабильного RAG. Не на старте.

**Не VRAM, а tok/s GPU.** Рост базы RAG не требует больше VRAM; может потребовать больше RAM и лучший reranker.
